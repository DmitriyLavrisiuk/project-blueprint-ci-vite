# CLAUDE.md

Тестовый проект скилла: React, ветка vite.

## Начало сессии и документация

- В начале сессии — `docs/STATUS.md` (что работает и что в работе), затем версия в работе в `docs/ROADMAP.md`.
- Карта документации, когда что читать и правила её ведения — `docs/README.md`. У каждого документа шапка: на что отвечает, где источник правды. Документ, который относится к задаче, читай целиком.
- Стандарты кода — в `.claude/rules/`: правило подгружается само, когда читаешь или правишь файл его типа. При создании файла оно приходит только после записи, поэтому перед новым файлом прочитай соседний того же типа.

- Перед UI-кодом — `docs/ui/README.md`.

## Как работаем

Подробно — `docs/WORKFLOW.md`.
- Вид нового компонента — сначала артефакт с вариантами, код — после выбора владельца.
- Коммит, тег, выкатка и пуш — только по команде владельца.
- Рабочие файлы — в папках `.tmp/` по назначению; своё убирай в конце задачи.
- После значимой задачи — `docs/STATUS.md` перезаписью, строка в `CHANGELOG.md` в `[Unreleased]`, отметка в `docs/ROADMAP.md`.

```bash

npm run lint       # Biome: линт и формат
npm run format     # Biome: формат
npm run typecheck  # tsc -b
npm test           # Vitest
npm run build      # сборка
```

## Принципы работы (обязательны)

1. **Думай до кода.** Не выбирай интерпретацию молча — если вариантов несколько, покажи их. Допущения называй явно; если что-то непонятно — остановись и спроси. Если есть более простое решение — предложи его.
2. **Минимализм.** Минимум кода, решающий задачу. Ничего спекулятивного: ни фич сверх запрошенного, ни абстракций для одноразового кода, ни «гибкости на будущее». 200 строк, которые могли быть 50 — переписать.
3. **Хирургические правки.** Трогай только то, что нужно для задачи. Не «улучшай» соседний код, комментарии и форматирование; не рефактори работающее; повторяй существующий стиль. Убирай только те импорты/переменные, которые осиротели из-за ТВОИХ правок. Замеченный чужой мёртвый код — упомяни, не удаляй.
4. **Goal-driven.** Превращай задачу в проверяемую цель до начала работы («исправь баг» → «напиши тест, воспроизводящий баг, добейся его прохождения»). Для многошаговых задач — краткий план, у каждого шага критерий проверки.

## Архитектурные правила

- Правил, которые не проверит линтер, пока нет: дополним по мере работы.

## Когда сомневаешься

Если задача затрагивает безопасность, миграции — сначала опиши план и спроси подтверждение, не пиши код сразу.
